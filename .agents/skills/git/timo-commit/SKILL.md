# Timo 커밋

## 트리거와 단계 경계

- **"커밋해줘", "커밋 만들어줘", "커밋 계획 세워줘", "staged 변경 정리해줘"**: Phase 1만 수행한다. 커밋별 메시지·파일·이유를 제시하고 **승인을 기다린다**. 스테이징이나 커밋은 하지 않는다.
- **"커밋 계획 승인", "제시한 계획대로 커밋해줘"**: 직전에 제시한 계획이 있고 변경 범위가 그대로일 때만 Phase 2를 수행한다. 변경이 달라졌으면 다시 계획을 제시한다.
- 구현·푸시·PR 요청만으로 이 스킬을 실행해 커밋하지 않는다. 한 요청에 여러 단계가 있어도 커밋 계획 또는 승인된 커밋까지만 하고 멈춘다.

커밋 형식과 타입의 기준은 [팀 규칙](../../../../docs/conventions/git-convention.md)의 **커밋** 항목이다. 이 저장소의 형식은 `[#이슈번호] type(scope): 한국어 요약`이며, 범위가 모호하면 scope를 생략한다. 본문을 쓰면 실제 변경과 검증 결과를 `~했습니다` 체로 적는다.

## 1. 범위와 비밀정보 확인

1. `git status --short --branch`, staged·unstaged **파일명**과 새 파일 목록을 확인한다. 이번 요청에서 만든 변경과 기존·무관한 변경을 구분하고, 브랜치의 이슈 번호가 불확실하면 추측하지 않는다.
2. 커밋 후보 파일의 경로와 내용에서 `.env`, 인증서·개인키, 실제 비밀번호·API 키·토큰·secret 값을 **노출하지 않고** 먼저 검사한다. 의심스러운 값이 있으면 파일명만 알리고 커밋을 멈춘다. `token` 같은 정상적인 식별자만으로 비밀정보라고 단정하지 않는다.
3. 비밀정보 검사를 통과한 뒤 staged·unstaged 후보 diff를 검토한다. **staged 변경 정리만 요청받았다면** staged 파일만 다룬다. 이번 작업의 커밋을 요청받았다면 이번 작업에서 만든 unstaged·새 파일도 후보에 포함할 수 있지만, 기존의 무관한 변경은 스테이징하거나 되돌리지 않는다.

## 2. Phase 1 — 작은 커밋 계획

- 한 커밋은 **하나의 검토 가능한 변경 이유**만 담는다. 같은 기능 안에서도 의존성·설정, 도메인 모델·영속성, 서비스 로직, Controller·DTO·OpenAPI, 문서는 분리 가능한 경우 각각 별도 커밋으로 계획한다. 서로 다른 기능·버그도 나누고, 한 파일 안의 독립 변경은 patch 단위로 나눈다.
- 각 커밋은 가능하면 그 상태로 빌드 가능해야 한다. 서로 강하게 결합된 파일은 억지로 쪼개 빌드를 깨지 말고 한 작은 단위로 묶는다. 모든 변경을 한 커밋에 넣는 통 커밋은 피한다.
- **커밋 번호, 팀 형식의 메시지, 포함 파일·hunk, 변경 이유, 검증 결과**를 계획표로 보여준다. 후보 변경의 공백 검사와 변경에 맞는 검증을 수행한다. Java 변경은 `./gradlew build`를 실행한다. 실패를 해결하지 못하면 계획과 실패 원인을 보고하고 커밋을 진행하지 않는다.
- 계획을 보여준 뒤 사용자 승인을 기다린다. 승인 전에는 `git add`나 `git commit`을 실행하지 않는다.

## 3. Phase 2 — 승인된 커밋 실행

- 먼저 `git status`와 후보 diff를 다시 확인한다. 계획 이후 변경이 생겼다면 실행하지 않고 수정된 계획을 제시한다.
- 승인받은 파일·hunk만 순서대로 스테이징한다. 한 파일에 이번 작업과 무관한 변경이 섞여 있으면 해당 부분을 분리할 수 있을 때만 포함한다. 각 커밋 전 `git diff --cached`와 `git diff --cached --check`를 확인하고 계획한 작은 단위로 커밋한다. `git add .`와 `--no-verify`를 사용하지 않는다.
- `git log --oneline -n <커밋 수>`로 결과를 확인하고 커밋 해시, 포함 파일, 검증 결과를 보고한다.
- 커밋 결과를 보고하고 멈춘다. 푸시·PR·머지는 다음 사용자 명령 없이 진행하지 않는다.
